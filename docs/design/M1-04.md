# M1-04 · IPC protocol and the app shell — design brief

> The first screen of the product, **composed from `@liminal/ui`**. Card:
> [`docs/specs/M1-sound/M1-04.md`](../specs/M1-sound/M1-04.md).
> Vocabulary: [`M1-07.md`](M1-07.md) (tokens in §1, the rules in §2, each component in §3–§9) and
> [`components.md`](components.md). Language: [`principles.md`](principles.md). Controls:
> [`../product/controls.md`](../product/controls.md).
> The implementation follows this brief; `ui-quality-reviewer` and `usability-reviewer` check the
> result against the numbered **Measurements**.

**This is a rewrite.** The first version of this brief was written before `@liminal/ui` existed and
described a token system the app owned in a stylesheet of its own. That file is deleted and that
work is gone from the branch. The rule now: **the screen composes and restyles
nothing.** Every colour, space, radius, type step and duration comes from `@liminal/ui/tokens.css`
by name; every control is `Transport`, `Readout`, `Slider`, `Toggle`, `Select` or `ErrorStrip`; and
where the catalogue has no answer, this brief names the gap instead of inventing a local style
(**Components › Catalogue gaps**).

## Job

**Open the app, see what is loaded, press play, hear it at a level that is not too loud, and know
where in the music you are.** Flows: **F0** (set up the sound) and **F1** (first run → music), with
**F5** (recover) as the one thing that may interrupt them.

The rows this card delivers from `controls.md`: **Master volume**, **Mute**, **Output device**
(Output — immediate), **Play / Stop** and **Readout** (Transport — immediate), and **Error strip**
(Seeing). Everything else — reference, prompt, timeline, layers, filter, cue, energy — is M4–M5 and
does not appear, not even greyed out.

## The theme is dark, and the screen says so

**Dark, always, until the person chooses otherwise.** The app opens dark whatever the machine
prefers; the system preference does not decide (`principles.md › The feel`, decided 2026-09-06,
applied from this card).

What carries it: **`data-theme="dark"` on the root element**, written into
`apps/desktop/src/renderer/index.html` as `<html lang="en" data-theme="dark">`. Nothing else is
needed, because `tokens.css` is already built for it: its light block is
`:root:where(:not([data-theme="dark"]))` inside the media query, so an explicit `data-theme="dark"`
switches the system preference off without any extra CSS and without touching the package. When a
theme setting arrives (M5, `controls.md › Settings`), it writes that same attribute from the stored
preference at boot; with nothing stored, dark.

The window's own background already agrees: `mainWindowOptions` takes `WINDOW_BACKGROUND` from
`@liminal/ui/colours`, which reads `--color-surface` out of the `:root` block — the dark value. No
flash of a colour the stylesheet does not know, and no hex in `main`.

## Layout

### Regions

Three, top to bottom, in one full-height column, plus the error slot inside the stage.

| Region | Element | Holds | Height |
|---|---|---|---|
| deck bar | `<section class="shell-deck" aria-label="Transport and the numbers">` | `Transport` (left) · `Readout` (right) | `--shell-deck-height` 88, fixed |
| stage | `<main class="shell-stage">` | the error slot at the top; the set's name and one hint line, centred | fills the rest |
| output bar | `<section class="shell-output" aria-label="Output">` | volume · mute (left) · output device (right) | `--shell-deck-height` 88, fixed |

The deck bar is `M1-07 › §10`'s, now with real data: `background: var(--color-surface-2)`,
`border-bottom: var(--border-width) solid var(--color-line)`. The output bar is its mirror —
same height token, `--color-surface-2`, and `border-top` instead of `border-bottom`. Reusing
`--shell-deck-height` for both is deliberate: two bars of the same weight framing a quiet stage
reads as a booth, and it adds no token.

**Each bar lays its contents inside an inner content column, and this corrects a defect shipped
with M1-07.** `M1-07 › §10` states that at 1920 "the deck bar stays full-bleed; its contents align
to the content column's edges", but `shell.css` only ever sets `padding-inline`, so the rule was
never built. The evidence recorded for M1-07 shows the result: at 1920 the transport sits at
`x = 32` while the content column starts at `x = 360`, and the deck bar's contents float 328 px away
from everything below them. This card rebuilds that CSS, so this is where it is fixed.

The rule, plainly, so it cannot be missed twice: **the deck bar and the output bar keep their own
`padding-inline`, and each wraps its contents in one element that carries**

```css
width: 100%;
max-width: var(--shell-content-max);
margin-inline: auto;
```

**— the same box the stage uses.** `padding-inline` alone does not do this and never did. The bars
themselves stay full-bleed, so the surface and the border still run edge to edge; only their
contents are constrained. The consequence is measurable and is **M7**: at every width, the Play
button, the set's name and the volume slider start at the same `x`, and `Readout` and the device
block end at the same one.

**Every control lives in a bar; the stage holds only text.** That is what makes the error strip
safe. When a strip appears it is inserted at the top of the stage, in flow: the deck bar is above it
and does not move, the output bar is below it and is pinned to the bottom of the column, and the
only thing that shifts is the centred name and hint — no target, no drag in progress, nothing a hand
is reaching for. The old brief solved the same problem by taking the strip out of flow with
`position: absolute`, plus arithmetic proving it could never cover the readout and a window
`minHeight` to hold the proof together. None of that is needed now. Stop, volume and mute stay
exactly where they were, measurably (**M14**).

Nothing is a modal, ever (`principles.md › What we do not do`).

### What changes with width

| | 1024 | 1440 | 1920 |
|---|---|---|---|
| bar padding-inline | `--space-5` 24 | `--space-6` 32 | `--space-6` 32 |
| stage padding | `--space-5` 24 | `--space-6` 32 | `--space-6` 32 |
| content column | fluid, 976 | fluid, 1376 | `--shell-content-max` 1200, centred |
| side gutters | 24 | 32 | 360 |
| every control's size | identical | identical | identical |

No control changes size at any width and no type step is responsive. Only the horizontal distance
between the left group and the right group grows, because both bars are `justify-content:
space-between` — the deck bar already is, and the output bar matches it so the two read as one
system. Above 1200 px the extra width is spent on emptiness, which is what "a booth at night, not a
spreadsheet" buys.

Below 1024 the layout is not designed (`CLAUDE.md › Quality targets`: desktop only). The window
opens at 1440 × 900.

### The two widths inside the output bar

The output bar needs two horizontal sizes the catalogue does not give, because `Slider` is
`width: 100%` of its box and `Select`'s trigger grows with its text:

- the volume block: `width: calc(var(--space-8) * 5)` → **320 px**;
- the device trigger: `max-width: calc(var(--space-8) * 4)` → **256 px**, with the text ellipsised.

Both are arithmetic on an existing token, in the shape `M1-07 › §2` already permits for `Readout`'s
`ch` widths — **not** a new value and not a new token; the grep gate passes. A cap on the device
trigger is what keeps a long real name from reflowing the bar: the measured names on this machine
run to `Alto-falantes (MacBook Pro) (Built-in)` and `Microsoft Teams Audio Device (Virtual)`, past
what 256 px holds. The trigger ellipsises and **never grows to fit a name** (**M11**); the open list
is Radix's and shows every name in full.

If the owner prefers these two to be named tokens beside `--shell-deck-height` and
`--shell-content-max` in `@liminal/ui`, that is **Decided › D4** — the role would be "the width of
the shell's volume block" and "the widest the device trigger may get", and the values stay the ones
above.

### 1 · `Transport` — `transport`

`size="lg"`: the main button 44 tall × ≥ 96 wide, the chip 28. It already carries state without
colour — the word in the chip, the shape in the chip, the label and the icon of the main button — so
this screen adds no styling of its own to it.

**One button, and it says what it does.** This product has no pause: `packages/engine/src/engine.ts`
has `play` and `stop` and nothing else. So the transport on this screen is a two-state toggle in one
slot — **`Play` when nothing is playing, `Stop` while it plays** — primary and enabled in both, with
no second, permanently half-dead stop button beside it. The prop that asks for this is `stopOnly`
(**D1**, rewritten; the first version of D1 is gone and why is below).

**What the first version did, and why it is gone.** It passed `canPause={false}`, which kept the word
`Play` while playing and **disabled** the button, with the sentence `This set can only be stopped,
not paused.` carried only as visually hidden text for `aria-describedby`. Two things were wrong, and
`evidence/M1-04/playing-1440.png` shows both next to `open-1440.png`: the one orange control on the
screen turned flat grey — the same treatment as "still loading" and "no output device" — at the exact
moment the music started and the product should have been confirming that it works; and the sentence
explaining it was never shown to anyone using a mouse. Disabled is the treatment for *something is
wrong or not ready yet*. "This product has no pause" is neither. A screen must not borrow the fault
treatment to say a fault-free thing, and it must not put its only explanation where only a screen
reader can find it.

**The rule this screen now holds to, everywhere:** *no control is disabled unless its reason is also
in visible words on the screen.* The reason keeps travelling on `disabledReason` for speech; that is
a second channel, never the only one. Below, every disabled row names where its words are visible.

**State mapping.** The store's `Transport` type is `'stopped' | 'starting' | 'playing' | 'ended'`;
the component's is `'stopped' | 'starting' | 'playing' | 'paused'`.

| Store | `state` | Main button | `canPlay` | `disabledReason` | Chip | Where the reason is visible |
|---|---|---|---|---|---|---|
| no document yet | `stopped` | `Play`, disabled | `false` | `The set is still loading.` | Stopped | the hint: `The set is still loading.` |
| load gave up (5 s) | `stopped` | `Play`, disabled | `false` | `The set did not load.` | Stopped | the hint: `Nothing is loaded yet.`, and the strip: `The set did not load.` |
| no output device at all | `stopped` | `Play`, disabled | `false` | `Connect speakers or headphones first.` | Stopped | the hint: `No output device. Connect speakers or headphones.` |
| ready | `stopped` | `Play`, enabled | `true` | — | Stopped | — |
| the audio context is resuming | `starting` | loading, reads `Starting…` | `true` | — | Starting… | — |
| playing | `playing` | **`Stop`, enabled** | `true` | — | Playing | — |
| ended (bar 16 played out) | `stopped` | `Play`, enabled | `true` | — | Stopped | — |

**The three disabled rows stay disabled, and they are not the defect the review found.** In all
three, nothing can be played: there is no set, or there is nowhere to play it. That is exactly what
disabled means, and in all three the hint line in the middle of the stage already carries the reason
in the person's words — it is the largest text on an otherwise empty screen, and the load failure
says it twice, in the strip as well. The playing case was the only one where the reason existed
nowhere on screen, and it was also the only one that was not a fault. The fix removes that case
rather than papering over it.

**Three things the toggle has to get right, each measured.**

1. **Nothing moves.** `Play` and `Stop` are both four characters with a 20 px icon, so both land on
   `--control-min-width-lg` (96) and the button's rect is identical in `open` and `playing`
   (**M15**). The chip sits at the same `x` in both states because the button before it does.
2. **A second click.** While `starting`, the main button is `loading`, which the component already
   renders as `aria-disabled` and which swallows the click — so the double-click that follows an
   eager first press does nothing. Once playing, a second click stops the music, which is what the
   toggle in every player does, and one more click starts it again from the top.
3. **Speech.** The button's accessible name changes from `Play` to `Stop`; the chip's polite live
   region says `Playing`. No third announcement is added, and the chip stays the only live region in
   the deck bar.

**`beatPulseKey`** is `bar * meter.beatsPerBar + beat` from the position the renderer reads off the
engine, so the chip ticks with the music and nothing else animates.

**`ended` shows `stopped` and the readout returns to `1:1`.** Pressing play starts the set from the
top, so a readout frozen at bar 16 would promise a resume that does not exist. The hint line says
what happened.

The package change `stopOnly` asks for is in **Catalogue gaps › 1** and **D1**.

### 2 · `Readout` — `readout`

`size="lg"`: group height 64, primary values `--text-5`, all `--font-mono` with `tabular-nums` and a
fixed `ch` width per field, so no digit change moves anything.

| Prop | Source | Empty |
|---|---|---|
| `tempo` | `score.tempo.bpm` | `null` → `—` |
| `musicalKey` | `score.key`, as `"A min"` — tonic, space, short mode, lower case, never `Am` | `null` → `—` |
| `bar` / `beat` | the engine's `position()`, **+1 each**: one-based, so a stopped transport reads `1:1` and never `0:0` | `null` → `—` |
| `elapsedMs` | `ticksToSeconds(absoluteTick(position, score.meter), score.tempo.bpm) * 1000` — `Position.tick` is the tick inside the beat, so the absolute tick is rebuilt from the bar and the beat | `null` → `—` |
| `playing` | `transport === 'playing'` | — |

**The position is read from the engine, not from IPC.** `transport:position` fires once per bar and
would freeze the beat digit for a whole bar. The renderer runs a `requestAnimationFrame` loop over
`engine.position()` for the screen, and sends the bar to `main` on the channel. `Readout` has no
live region, by contract: four announcements a bar is unusable with a screen reader.

`"A min"` fits `--readout-key-ch: 6`, which was sized for `"F# min"`. The mode words are the
schema's six (`major`, `minor`, `dorian`, `phrygian`, `lydian`, `mixolydian`) shortened to
`maj`, `min`, `dor`, `phr`, `lyd`, `mix` so every one of them fits the reserved box.

### 3 · The set's name and the hint line — `shell-title`, `shell-hint`

Two lines of text centred in the stage, the only things there at rest.

- **`shell-title`**: `<h1>`, `--font-display`, `--text-4`, `--weight-semibold`, `--tracking-tight`,
  `--leading-snug`, `--color-ink`. Copy: `score.lineage?.label` when present, otherwise
  **`Example set`** — the words `usability.md › The empty state is a state` already uses. While
  nothing is loaded: `Loading the set…` in `--color-muted`.
- **`shell-hint`**: `<p>`, `--font-body`, `--text-1`, `--color-muted`, `--space-2` under the title.
  One sentence, never two.

| State | Hint |
|---|---|
| no document yet | `The set is still loading.` |
| load gave up | `Nothing is loaded yet.` |
| ready | `Ready. Press play.` |
| starting | unchanged from the previous state — the chip already says `Starting…` |
| playing | `Playing. This example is sixteen bars long.` |
| ended | `The set reached the end. Press play to hear it again.` |
| no output device | `No output device. Connect speakers or headphones.` |

**The hint is not a live region.** Every change on this screen that is worth announcing is announced
by something that already owns it: `Transport`'s chip is `aria-live="polite"` for transport state,
and `ErrorStrip` is `role="alert"` for anything that went wrong. Making the hint a third region
would double every announcement — press play and hear "Playing" twice.

"Playing. This example is sixteen bars long." is deliberate: F1 asks the screen to say the music will
not stop, and in M1 it **does** stop after sixteen bars. Saying otherwise would be a lie the very
first run tells. The endless set arrives in M4 and takes that sentence with it.

### 4 · Volume — `output-volume`

`Slider`, `min={-60}`, `max={0}`, `step={1}`, `largeStep={6}`, `ticks={[-12]}`, `showValue="always"`.
The label row shows `Volume` on the left and the value on the right; the track is below it. The
value is always on screen and updates on every step, which is what makes a drag readable
(`components.md`: a value shows while changing). The tick marks the safe level, so −12 dB is a place
you can find again by eye.

`format` returns the word `silent` at −60 dB and `−12 dB` shaped text everywhere else, with a real minus sign (U+2212) and integers only.
At the bottom of the range the output is silent and the word says so instead of printing `−∞`, which
speech mangles. `Slider` feeds `format`'s result to both the visible value and `aria-valuetext`, so
a screen reader says "minus twelve dB" and "silent" (**Catalogue gaps › 4** if that reading turns out
to be wrong on VoiceOver).

**The value at first run is −12 dB, and it never comes back louder.** `preferences.ts` already
enforces the rule; the screen's job is to show it and to never hand back a louder number:

- first run → `SAFE_OUTPUT_GAIN_DB` = −12 dB;
- a stored value that parses and sits inside `OUTPUT_GAIN_DB` (−60…0) is restored **exactly as
  written**; anything missing, corrupt, wrongly typed or out of range falls back to −12 dB, never to
  the top of the range;
- so the only value the app can come back to is one a person set (`usability.md › heuristic 3`);
- it lives in `app.getPath('userData')`, per machine, never in the document.

`onValueChange` moves the engine's output gain **now** (`setOutputGain`); `onValueCommit` is what
sends `output:volume` to `main` to be written. Sound reacts to every step, the disk is written once
per gesture.

| State | What is on screen |
|---|---|
| rest | range in `--color-accent`, value at its dB number |
| hover | thumb scales 1.1 over `--duration-1` (the component's own) |
| focus | ring 2 px `--color-focus`, offset 2, around the thumb |
| dragging | range in `--color-accent-active`, value updating at every step |
| muted | unchanged and still enabled — lowering the volume while muted and then unmuting must be quiet, not loud |
| disabled | never on this screen. Volume works before the set arrives and after it ends |

### 5 · Mute — `output-mute`

`Toggle`, `tone="warn"`, `label="Mute"`, `size="md"` (36 tall). The label does **not** change with
state: the filled-versus-hollow dot carries it without colour, `aria-pressed` carries it in the
accessibility tree, and `stateLabel={{ on: 'muted', off: 'not muted' }}` carries it in speech. A
label that swaps between "Mute" and "Muted" changes the button's width and moves a target under the
cursor.

Muting never stops the transport: `bar:beat` keeps advancing (the card's gate), and the engine's
`setMuted` acts on the output stage after the master limiter, so the soundcheck and any export
measure the same audio with and without it (`controls.md › Two kinds of control`).

| State | Look |
|---|---|
| off, rest | `surface-2` / `line-strong` / `ink`, dot hollow |
| off, hover | `surface-3` |
| on | `signal-warn` fill, dot filled |
| focus | ring 2 / 2 |
| disabled | never on this screen |

### 6 · Output device — `output-device`

`Select`, `label="Output"` (visible, above the trigger), `size="md"`, trigger capped at 256 px with
the text ellipsised. The trigger shows the device in use at rest, which is what F0 requires; the
open list marks the current one with a check in a fixed gutter, so selection is not colour-only.

`items` is built by the **renderer** from `enumerateDevices()`, kind `audiooutput`, with
`{ value: id, label }`; `System default` (`value: 'default'`) is always first when the runtime offers
it. The renderer enumerates on mount and again on every `devicechange`. **There is no permission
flow and no opt-in**: measured in this runtime, `enumerateDevices()` returns real ids and real labels
on first paint with no `getUserMedia` call and no macOS dialog (`docs/memory/measurements.md`,
2026-09-06). Nothing on the first screen asks the person for anything.

**Why the renderer owns the list and `main` only the choice.** `setSinkId` accepts only ids that
`enumerateDevices()` produced, and Chromium builds each as a hash of the origin, the real device id
and a per-profile salt, resolvable only inside Chromium
([MediaDeviceSalt](https://chromium.googlesource.com/chromium/src/+/main/components/media_device_salt/README.md)).
An OS-side name cannot be matched to an id the renderer can switch with, so a picker built in `main`
could list devices it is unable to select — worse than listing none. `'default'` is the one unsalted
exception, which is why `System default` always works. `output:device` returning
`{ devices, selected }` therefore only ever echoes a list the renderer gave it.

| Store state | `Select` | Rest of the screen |
|---|---|---|
| the ordinary case | every device listed, the current one selected and readable at rest | — |
| the list is still being enumerated | `loading` → spinner in place of the chevron, `aria-busy`, trigger not openable, the current value still readable | — |
| a switch is in flight (`setSinkId` pending) | `loading`, the trigger still showing the **previous** device until the switch lands | — |
| the switch succeeded | the new device selected; no confirmation, no restart | — |
| the switch failed | the trigger returns to the previous device | the `sink-unavailable` strip |
| only `System default` came back | one item, **enabled** | — |
| no `audiooutput` at all | `items` empty → the trigger reads `No output device` in `--color-muted`, `aria-disabled`, and opening shows one non-selectable item with the same words | Play disabled with `Connect speakers or headphones first.`; hint line says the same in the person's words |
| the device disappears while playing | the value falls back to `System default`; playback does not stop | the `device-lost` strip |

The single-device case stays **enabled**, which is a change from the old brief. Disabling it paints
the only device name in the disabled treatment — `--color-muted` on `--color-surface-2` — and the
one thing F0 asks to be readable becomes the faintest text in the bar. Nothing is broken and nothing
is missing; a list of one is a list.

### 7 · `ErrorStrip` — `error-strip` (F5)

dismissal={{ onDismiss: shell.dismiss, focusOnDismiss: playRef }}

### What `completeness.md` asks for and this screen does not have

- **"Anything that plays over time expects pause, what comes next, and elapsed."** Elapsed is here,
  in `Readout`. Pause is **not**: the engine has no pause, so the control would be a lie
  (**Catalogue gaps › 1**). The screen does not apologise for it either — the main button offers
  `Stop` while playing, so there is no pause on screen to explain and no greyed-out ghost of one. "What comes next" has no answer while the only document is a sixteen-bar
  fixture; it arrives with the queue in M4.
- **"Any list expects reorder, remove, an empty state."** The device `Select` is a picker of the
  system's options, not a list the person owns; there is nothing to reorder or remove. Its empty case
  is designed above and uses the component's own `emptyLabel`.
- **"Settings: one place, grouped."** No settings panel in M1. The theme is dark and fixed (the
  attribute is on the root, ready for the panel); reduced motion follows the system through
  `tokens.css`; the safe start volume is fixed at −12 dB.
- **"Anything that takes a while expects progress, an estimate, cancel, and an explicit error with
  retry."** The only wait here is one local file read across one IPC message — fast enough that a
  progress bar would flash and lie, and there is nothing to cancel. What the row really demands is
  that the wait **ends**, so it does: after **5 s** with no `score:load`, the strip says
  `The set did not load.` The screen never sits on `The set is still loading.` forever.
- **"Any decision the system makes expects a why."** M1 makes no decisions; the brain is M4.

## Keyboard and accessibility

### Focus order

Focus order is DOM order, and no element carries a positive `tabindex`.

| Ready, no strip | With a strip | Loading (the main button disabled) |
|---|---|---|
| the main button | the main button | volume thumb |
| volume thumb | strip action | mute |
| mute | strip dismiss | device |
| device | volume thumb | |
| | mute | |
| | device | |

The transport is one focus stop in every state, because it is one button. Nothing enters or leaves
the tab order when the music starts — the button that had focus keeps it and changes its word.

The strip sits between the two bars in the DOM, so `Tab` reaches the transport first and the error
second. That is the right order for this screen: the strip announces itself (`role="alert"`) wherever
focus is, and the control someone lunges for in a bad moment is Stop. Focus never jumps on its own
when a strip appears — an unasked focus move while music plays is worse than an extra `Tab`.

A disabled `<button>` leaves the tab order, which is why the loading column starts at the volume.
That is the one place on this screen where the tab order changes with state.

### The map

| Key | Does | Scope |
|---|---|---|
| `Space` | play when stopped, stop when playing — the same two actions the main button offers | global, under the guard |
| `M` | toggles mute | global, under the guard |
| `↑` / `↓` | volume ± 1 dB | global, under the guard |
| `0`–`9` | volume to `−60 + 6n` dB | global, under the guard |
| `Tab` / `Shift+Tab` | the order above | native |
| `Enter` / `Space` | activates the focused button | native |
| `←` `→` `↑` `↓` | ± `step` on the focused slider | Radix |
| `PageUp` / `PageDown` | ± 6 dB on the focused slider | Radix, via `largeStep` |
| `Home` / `End` | −60 dB / 0 dB on the focused slider | Radix |
| `Enter`, `Space`, `↑`, `↓` | opens the focused device picker; then arrows move, type-ahead selects, `Enter` commits, `Esc` closes and returns focus | Radix |

**One guard, written in terms of what has focus:**

> The global handler returns early — doing nothing, preventing nothing — whenever the key it received
> already **does something native** on `document.activeElement`. The focused element always wins.

| Focused | `Space` | `↑` / `↓` | `0`–`9` | `M` |
|---|---|---|---|---|
| nothing (`<body>`) | · | · | · | · |
| a `<button>` (the transport, mute, strip action, strip dismiss) | native: activates | · | · | · |
| the device trigger | native: opens | native: opens | native: type-ahead | native: type-ahead |
| the volume thumb (`role="slider"`) | · | native: ± 1 dB, the same result | · | · |

`·` means the key is not native there and the global handler acts.

The blanket form — "return early whenever a button, a select or the slider has focus" — is **wrong**,
and this brief does not say it: the moment someone presses Play, focus sits on a `<button>`, and
`M`, `↑`, `↓` and the digits would all go dead. The card requires those keys to work without the
mouse, so the guard is per key, not per element. Three traps it dodges, each of which passes every
unit test while being broken on screen:

1. `Space` on the focused main button fires twice — the button activates, then the global handler
   toggles the transport back. The toggle makes this worse, not better: press, play, press, stop,
   and the second press lands back where it started.
2. `Space` on the focused device trigger opens the picker **and** starts or stops the music. The
   trigger is a `<button>`, so a guard written against `<select>` misses it, and one written against
   buttons kills `M` while Play has focus.
3. `↑`/`↓` and the digits on the focused device trigger are Radix's own opening and type-ahead;
   without the guard, choosing a device would also move the volume.

When the handler does act, it calls `preventDefault()` — for `Space`, so the window never scrolls.

`0`–`9` maps to `−60 + 6n` dB (`gainForDigit` in `shortcuts.ts`): `0` → −60 (silent), `5` → −30,
`9` → −6. The top of the range is reachable only by dragging or by `End`, so a stray number key can
never jump the output to full.

## Catalogue gaps

Named here rather than styled around locally, in the order of how much they cost. The first two are
**decided** (D1, D2): both are new optional props whose defaults preserve today's behaviour, so they
are built in this card together with the screen, and each gets its catalogue row and its story.

**1 · `Transport` offers pause and M1 has none.** In `playing` the main button becomes `Pause` and
calls `onPause`, but `packages/engine/src/engine.ts` has `play` and `stop` and nothing else, and this
card adds no pause channel.
*Smallest addition:* an optional prop **`stopOnly`** on `Transport`, default `false`, which preserves
every consumer. With `stopOnly`, the main button is `Play` when the state is not `playing` and
`Stop` while it is, calling `onPlay` and `onStop`; the separate icon-only stop button is not
rendered, and `onPause` is never called — so `onPause` becomes optional in the props type, which is
also backwards compatible. `canPlay` and `disabledReason` keep their meaning for the states where
nothing can be played.
*Rejected, and why:* (i) `canPause={false}` with the button left as a disabled `Play` — that was the
first D1, and it painted the fault treatment onto a fault-free state and hid its own explanation
(§ *Components and states › 1*); (ii) `onPause={onStop}` — a button whose word lies; (iii) rendering
no main button at all while playing — it moves the chip and the stop target under a hand that has
just clicked, and it takes away the confirmation that the press worked. Decided: **D1**.

**2 · Nothing hands back a ref to the play button.** `ErrorStrip`'s `dismissal.focusOnDismiss` needs a
focusable element, and `Transport`'s `ref` is its container `<div>`, which cannot take focus.
*Smallest addition:* an optional `playRef?: Ref<HTMLButtonElement>` on `Transport`, forwarded to the
main `Button`, which already forwards its own ref — additive, default undefined.
*Fallback with no package change:* point `focusOnDismiss` at the device `Select`'s trigger, which does
expose a ref — right for the two device strips and arbitrary for the other four, so it is not taken.
Decided: **D2**.

**3 · There is no component for a screen's title or for a one-line hint.** Both are plain text with no
state and no interaction, so they are markup in the shell (`<h1>`, `<p>`) styled from tokens — a
composite, not a restyle, and `components.md` puts composites in the app. If a second screen needs
the same pair, they are promoted to `@liminal/ui` together and get their own catalogue row.

**4 · `Slider` gives one string to both the eye and the screen reader.** `format` feeds the visible
value **and** `aria-valuetext`. `−12 dB` with U+2212 is right on screen; whether every screen reader
says "minus" for it is a question for the listening gate. *If it reads badly:* an optional
`valueText?: (value: number) => string` on `Slider`, defaulting to `format` — additive and invisible
to every existing consumer. Try the one string first.

## Decisions and open questions

### Decided — the implementation and the reviewers read these as settled

**D1 · `Transport` gains `stopOnly`, and the transport is a Play / Stop toggle.** *Rewritten
2026-09-06, after the usability review of `evidence/M1-04/playing-1440.png`. This replaces the
earlier D1, which gave `Transport` a `canPause` prop and left the main button disabled while
playing. That version is not built; `canPause` comes out.*

A new optional prop, `stopOnly`, default `false`, which preserves every consumer that exists. This
screen passes `stopOnly`: the main button reads `Play` when nothing is playing and **`Stop` while it
plays**, is primary and enabled in both, and the separate icon-only stop button is not rendered.
`onPause` becomes optional in the props type and is never called in this mode.

**Why the first version had to go.** It disabled the main button while playing and carried its
explanation — `This set can only be stopped, not paused.` — only as visually hidden text for
`aria-describedby`. Measured on the built screen, the filled orange button the person had just
clicked turned flat grey at the moment the music started, in the same treatment used for "still
loading" and "no output device", with no words anywhere a sighted user could read them. Disabled
means *not ready or broken*; the absence of pause is neither, and the most prominent control on the
first screen must not read as broken at the one moment the product is proving it works.

**Why not simply show the sentence.** Putting `This set can only be stopped, not paused.` in the
hint line was the other candidate. It fixes the missing words but not the grey slab, it spends the
one hint line on an apology for a feature the product does not have, and it explains a control the
person never asked about. A button that says `Stop` needs no sentence.

**Why not remove the main button while playing.** The bar would reflow, the stop target would slide
under a hand that has just clicked, and the press would lose its confirmation. Nothing moves in the
toggle: `Play` and `Stop` both clamp to `--control-min-width-lg` (**M15**).

**The rule this settles for the whole screen:** no control is disabled unless its reason is also in
visible words on screen. The three remaining disabled cases — still loading, the load gave up, no
output device — already meet it: the hint line carries each reason in the person's words, and the
load failure repeats it in a strip. They keep `disabledReason` as well, so the reason is spoken at
the control too; hidden text is a second channel, never the only one.

`stopOnly` needs its row in `docs/design/components.md` (replacing the `canPause` entry on the
`Transport` row) and its own stories: `stopOnly` stopped, `stopOnly` starting, `stopOnly` playing.

**D2 · `Transport` gains `playRef`.** A new optional prop, `Ref<HTMLButtonElement>`, forwarded to the
main `Button`, which already forwards its own ref. Default undefined, so nothing changes for anyone
else. `ErrorStrip`'s `dismissal.focusOnDismiss` points at it, and dismissing a strip lands the person
on Play.

**D3 · The store's `Transport` union gains `'starting'`.** Set on click, cleared when the engine
reports it is running. It is the only way the screen answers within 100 ms while the audio context
resumes. If the resume turns out to be instant here, the state is passed through and never lingers —
measure it.

**D4 · The two widths in the output bar stay as `calc()` on `--space-8`.** `calc(var(--space-8) * 5)`
for the volume block, `calc(var(--space-8) * 4)` as the device trigger's cap. No new token, no loose
value, and the grep gate passes. If a second bar ever wants the same two sizes, they become named
tokens beside `--shell-deck-height` — one PR, no redesign.

**D5 · `Readout` shows elapsed.** From `ticksToSeconds(absoluteTick(position, meter), score.tempo.bpm)` — `Position.tick` is the tick inside the beat, so the absolute tick has to be rebuilt from the bar and the beat. A fourth em
dash beside three live numbers looks broken, and `controls.md` lands elapsed in this card.

Both package changes (D1, D2) are additive props with defaults that preserve today's behaviour, so
they need a row each in `docs/design/components.md` and a story each in `packages/ui`, in the same
PR (`components.md › The rules`).

### Still open

**Q1 · The document's name.** `Score` has no name field and `lineage.label` is optional.
(a) `lineage.label ?? "Example set"` — the words `usability.md` already uses, and what this brief is
written against; (b) add a required `name` to the score schema, a change to `@liminal/score` and
outside this card; (c) show the score `id`. Taking (a) unless told otherwise.

**Q2 · Retrying a load that never arrived.** `score:load` is `mainToRenderer`, so the renderer has no
way to ask again and the strip carries no action. (a) dismiss-only, as designed, and the person
reopens the app; (b) add a `score:request` channel so `Try again` can exist, which widens the card's
protocol; (c) have `main` resend on a timer. Taking (a); (b) is the natural fix when a second
document source arrives in M2.

### An offer, not a gate

**A design canvas.** The card does not set `design_review: true`, so nothing here waits on an
approval and the screen is built as soon as this brief is read. **The numbered Measurements are the
gate.** If the owner would like to look at the screen as a picture rather than as prose, a canvas of
`open`, `playing` and `device-lost` at 1440 can be published on request — before the build or after
it, either is useful. Setting `design_review: true` on the card is what would turn that offer into a
real gate; this brief does not do it.
