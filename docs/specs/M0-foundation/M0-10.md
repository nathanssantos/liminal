## Context

The repo is public and run like a company (`docs/product/strategy.md`). Strangers must understand
it in five minutes, contributors must know the process, and every milestone close is a release
(process §14). This card puts the scaffolding in place.

## What to do

- `CONTRIBUTING.md`: the process in one page for a human — specs as source, the board and its
  columns, the loop, English everywhere, no-comments rule, how to propose (an `idea` issue), how to
  ask the loop something (`question`, `research`).
- `CODE_OF_CONDUCT.md` (Contributor Covenant), `SECURITY.md` (how to report, no secrets in the tree).
- Issue templates: `bug`, `idea`, `research`, `decision` (the last two mirror the process labels);
  the PR template from M0-04 checked against process §3.5.
- `CHANGELOG.md` in Keep a Changelog form with an `Unreleased` section; the `/release` skill's
  `v0.0.0` entry for M0.
- `.github/workflows/release.yml`: on a `v*` tag, creates the GitHub Release from the changelog
  section.
- README: platform frame, what exists now, how to try it (M0: nothing to hear yet — say so), badges.

## Done when

- [ ] the four community files exist and GitHub's community profile shows them as present — proof: `gh api repos/nathanssantos/liminal/community/profile`.
- [ ] creating an issue offers the four templates and each carries the right label — proof: screenshot and `gh issue view` of one of each.
- [ ] pushing tag `v0.0.0` creates a Release whose body is the `CHANGELOG.md` M0 section — proof: `gh release view v0.0.0`.
- [ ] `open-source-steward` reports no `blocking` finding — proof: the agent's report.

## Out of scope

Packaging the app; signing; a website.
